# 实时流水线

流水线支持实时与定时两种执行模式。实时模式用于日志写入时转换与分流；定时模式查询已经落盘的数据，按时间窗口执行。实时模式当前支持日志、一个来源流、一个数据流输出节点，以及按顺序执行的内置处理和 VRL 函数。

## 配置

流水线保持「输入 → 处理 → 输出」。处理节点有两种类型：

- 常用逻辑：目前提供“数据分流”，支持固定目标流、按字段动态分流、前缀和兜底流。
- VRL 函数：解析、清洗和修改事件字段，可与内置处理交替使用。

每条事件按处理节点顺序执行。分流使用执行到该节点时的字段；后续 VRL 修改字段不会重新计算已选定的目标流。多个分流步骤以后一个结果为准。目标流存在独立的执行元数据中，不混入日志正文。

实时与定时模式都支持两种处理节点。定时模式拒绝分流回来源流，以免反复处理自身输出。

实时示例：输入 `default` → VRL 提取 `appname` → 常用逻辑按 `appname` 分流 → 数据流输出。

输出节点按处理结果写入，目标流不存在时自动创建。没有分流步骤时，使用输出节点配置的固定目标流。

“同时保留到源数据流”在实时输入节点配置，默认关闭；开启后保留转换前的原始日志。源流与目标流一致时仅写一条处理后的日志。所有副本均继续执行脱敏与 schema 校验。

字段查找优先使用完整字段名，再按点分隔访问嵌套对象。流名允许 ASCII 字母、数字、`_`、`-`、`.`，长度 1–255；不允许 `.`、`..` 或受保护的 `_molesignal`。不自动替换非法字符，以免不同应用被无意合并到同一流。

同一组织的同一来源流只能启用一条实时流水线。配置更新在后续写入批次生效；已经开始处理的批次继续使用读取到的配置。输出不再次触发流水线，避免循环。

## 错误与统计

VRL 执行失败或输出不是对象时，拒绝该事件并返回原始批次中的索引。存储/数据库故障返回错误，不写兜底流掩盖故障。不同目标流的写入不具备跨流原子性：部分流可能已成功，整批重试可能产生重复；不承诺 exactly-once。

每个目标流按进入转换前的事件字节数计量。保留源副本时，该源流也计入对应字节；组织层面的接入流量仍按入口请求计一次。响应的 accepted/rejected 按输入事件计数，不因保留副本翻倍。

实时流水线不产生定时任务运行记录，也不支持历史回填；列表的“等待接收”表示已启用配置，不表示已经收到数据。

## API

继续使用 `/api/v1/scheduled_pipelines` 管理接口，模式和路由存储于 `function_steps`，不新增数据库表或列。旧配置未指定 mode 时为 scheduled。

```json
{
  "name": "route-app-logs",
  "source_stream": "default",
  "target_stream": "default",
  "cron": "",
  "lookback_secs": 300,
  "enabled": true,
  "function_steps": {
    "mode": "realtime",
    "signal_type": "logs",
    "sources": ["default"],
    "sinks": ["default"],
    "retain_source": false,
    "steps": [
      {
        "transform_name": "route-app-logs",
        "kind": "builtin",
        "operation": "route",
        "routing": {
          "kind": "field",
          "field": "appname",
          "prefix": "",
          "fallback": "default"
        }
      }
    ]
  }
}
```

VRL 步骤使用 `{"kind":"vrl","transform_name":"parse","script":". = parse_json!(.message)"}`。旧步骤未指定 kind 时仍按 VRL 执行；旧版顶层 routing 在编辑时转换为末尾内置处理步骤，重新保存后使用新结构。
